# Pinterest campaign hierarchy and creative previews

Pinterest tools use the same registry and preview/apply policy in the CLI, local MCP and hosted MCP. Advertising creation is forced to `PAUSED` by the default policy. Every status, bid, budget, targeting or archive operation requires its own approved preview.

## Campaigns and ad groups

`pinterest_create_campaign` creates a campaign with Campaign Budget Optimization (CBO). Its daily/lifetime cap is an integer amount in account-currency micros. `pinterest_create_ad_group` verifies the parent campaign and keeps CBO budgets at campaign level. An existing non-CBO campaign instead requires a child budget.

Ad-group creation asks for the billable event, bid strategy and geographical targeting. Automatic targeting defaults to false and appears explicitly in the preview. MAX_BID requires a bid. CBO supports STANDARD pacing only. Some CBO scheduling features require Pinterest beta access.

`pinterest_get_entity` reads one verified campaign/ad group/ad by its native ID. `pinterest_ad_groups` and `pinterest_ads` provide paged configuration reads. Native array query parameters use **comma-separated values**: the live endpoint silently treated repeated status parameters as only their final value, causing historical/archived entities to disappear. Reporting and configuration reads share the corrected encoding.

`pinterest_update_ad_group` edits supplied name, schedule, targeting and optimization fields. Omitted targeting dimensions and optimization properties are preserved; supplied arrays replace their previous values. Conversion tags must belong to the selected advertiser. Monetary optimization targets, including native string-valued CPA goals, are included in policy deltas.

`pinterest_set_ad_group_budget` preserves an existing non-CBO daily/lifetime budget type. Use `pinterest_set_budget` for CBO campaigns. `pinterest_set_ad_group_bidding` checks current/proposed bids in micros. Parent and child serving statuses remain independent.

## Ads and Pin content

`pinterest_create_ad` creates a paused ad using an existing eligible Pin and verified advertiser-owned ad group. This does not change the original Pin. `pinterest_update_ad` edits name, destination and tracking fields. Pinterest permits replacing `pin_id` only on DRAFT ads; use a new paused ad for a different Pin after publication.

`pinterest_ads` can hydrate the Pins referenced by the selected advertiser's ads to display their actual copy and image/video media. The connected profile needs existing `boards:read` and `pins:read` permissions. A denied Pin read preserves the ad configuration and reports a warning. Hydration uses up to four concurrent requests and preview pages are capped at50 ads. Disable `include_pin_details` for larger configuration-only pages.

Ad-setting actions stay bound to the displayed advertiser and use the ordinary policy preview/apply gate. Editing a shared original Pin is a separate operation from editing an ad.

## Agent-managed original Pins and media

These named tools use Pinterest's [official v5 OpenAPI](https://github.com/pinterest/api-description/tree/main/v5) (5.28.0); no dashboard or browser upload is required. The existing ads-only OAuth scope is unchanged. Public board/Pin operations require the corresponding existing `boards:read`, `boards:write`, `pins:read` and `pins:write` grants plus native Business Access roles. Secret content additionally requires `boards:read_secret`, `boards:write_secret`, `pins:read_secret` and `pins:write_secret`; public-content scopes do not grant private-content access. Pin updates also require Pinterest's beta access. A tool being present does not establish those permissions.

Owners can explicitly opt in to public content through **Platforms → Pinterest → Enable Pin management**, or locally with `adport connect pinterest --pin-management`. The option requests the two Ads scopes plus `boards:read`, `boards:write`, `pins:read`, `pins:write` and `user_accounts:read`. Existing connections and ordinary ads-only connect flows are unchanged. The hosted opt-in is bound to its one-use encrypted OAuth transaction; callback query parameters cannot add permissions. The exchange must confirm every requested scope before replacing the stored grant. The app still needs Pinterest access to those scopes; this option does not bypass native app review or beta restrictions. Once authorized, normal asset work uses tools without a dashboard.

Secret content has a separate opt-in: **Enable secret Pin management** after the public grant, or `adport connect pinterest --secret-pins` locally. It includes the public permissions and explicitly adds the four `_secret` scopes above. Ordinary Ads and public Pin flows never request them. Reconnect preserves the explicitly granted capability; secret-scope verification and transaction binding follow the same rules. Pinterest app eligibility still applies. A default `SECRET` board creation needs this additional grant before apply.

1. Use `pinterest_boards` to discover the selected advertiser owner's boards and their current visibility. Collaborator boards are labeled but are not writable through these tools. `pinterest_create_board` creates a `SECRET` board by default. Explicit `PUBLIC` creation requires `confirm_publication`; `PROTECTED` creates an ad-only board named by Pinterest. Protected boards are not secret boards.
2. Stage exact source bytes with the [project media tools](creative-media.md#project-media-library), or use an absolute `file_path` from local CLI/stdio. `pinterest_create_image_pin` resolves the SHA-256-bound PNG/JPEG on the server and sends native `image_base64`; the agent does not reproduce provider base64. Supply `original_content: true`, an owned board ID and its exact `expected_board_privacy`. Public boards require `confirm_publication: true`. This creates original Pin content; creating or enabling an advertiser ad is a separate operation.
3. For video, preview/apply `pinterest_upload_video` with the source and SHA-256. Adport registers the native video and transfers the bytes using Pinterest's signed multipart instructions. OAuth is never forwarded to Storage. Read `pinterest_get_media_upload` using the returned native ID; only `succeeded` media can be used by `pinterest_create_video_pin`. Its cover image uses the selected keyframe in seconds. Native video processing can still reject codecs, duration or other eligibility.

Pinterest's `/media` endpoint is scoped to the credential's user, with no advertiser parameter. Video tools therefore verify the selected advertiser owner against that user and require existing `user_accounts:read` in addition to the media scopes; delegated advertisers with a different owner are rejected. Upload acceptance is separate from processing success. Failed or unknown registration/transfer is not retried; any returned native ID is retained for reconciliation. Pinterest exposes no delete-media endpoint in this contract.

`pinterest_get_board` reads one owned board's name, description, visibility, native counts and copy snapshot, with an inline edit form. `pinterest_update_board` changes only the supplied name or description; `null` clears the description. Privacy, Pins, sections and ad delivery are preserved. Pinterest controls ad-only board names, so those boards expose description editing only. Copy, owner or visibility changes invalidate the snapshot; independent count changes do not invalidate a copy edit. Preview and apply both reread the board. Pinterest does not document atomic conditional updates, so this is a fresh-state check rather than a provider compare-and-swap.

`pinterest_delete_empty_board` is a separate permanent cleanup operation for explicitly `SECRET`, non-ad-only owned boards. It requires the current copy snapshot, `confirm_permanent_deletion: true`, known zero Pin/collaborator/follower counts and empty native Pin and section collections. It rejects populated, public, protected or unknown state. Apply repeats those reads immediately before DELETE; no cascade parameters are sent. Stop concurrent board writers while deleting: Pinterest has no documented atomic empty-board conditional delete, so these checks cannot eliminate the final provider race. This tool never claims that project source media was removed.

`pinterest_pins` displays original copy/media with bookmark pagination, optionally for one owned board. `pinterest_get_pin` returns a current snapshot and an edit form for an explicitly owned, never-promoted Pin. `pinterest_update_pin` edits only supplied title, description, alternative text or link; `null` clears a field. Source bytes, board membership and delivery are preserved. Shared original content can change its existing organic display. `pinterest_delete_pin` permanently deletes the original after verifying its snapshot. Both operations reject promoted Pins or unknown promotion/ownership state; use a new replacement Pin for those cases. Native copy edits are beta and may be denied for the connected app. A changed copy, board privacy, owner or promotion flag invalidates the snapshot.

These operations are ordinary shared-registry tools: CLI, MCP and hosted REST all use the same preview/apply policy, protected-account checks, one-use approvals and audit log. Additive board/image/video creation is annotated as a write; copy replacement and deletion carry destructive hints. Every mutation still requires preview and apply.

## Discovery and cleanup

`pinterest_targeting_options` returns native targeting choices. `pinterest_audience_estimate` uses a non-binding read-only POST estimate. `pinterest_audiences` and `pinterest_conversion_tags` read existing configuration without uploading customer data, installing tracking or sending events.

`pinterest_archive_entity` verifies ownership and archives a campaign, ad group or ad. Batch failures retain any returned resource IDs for reconciliation before retrying; an incomplete or mismatched receipt is not reported as a successful apply.

## Keywords

Use `pinterest_keyword_context` to select an account, campaign or ad-group parent and obtain its current parent hash. The native account default returns account-level exclusions only; it does not enumerate campaign/ad-group keywords. `pinterest_keywords` supports bookmark pagination and match-type filters, returns a snapshot per keyword and provides guarded archive actions. `pinterest_get_keyword` finds one exact ID within the selected parent; Pinterest has no direct keyword-by-ID read, so this lookup is bounded to10,000 visible rows.

`pinterest_create_keywords` creates up to100 unique value/match-type pairs. Account and campaign parents accept `EXACT_NEGATIVE` or `PHRASE_NEGATIVE` only; ad groups also accept `BROAD`, `PHRASE` and `EXACT`. Keywords cannot be paused individually. Under `paused_creation`, positive additions require a paused parent ad group or campaign; existing serving parents are never silently paused. Keyword bids are deprecated in the native contract and are intentionally not sent or exposed as effective bid controls. Use the existing ad-group bidding tools instead.

`pinterest_archive_keywords` matches the current parent and each keyword snapshot, then sends native `archived: true`. Pinterest describes this as effective deletion: archived keywords disappear from parent lists and metrics. A safe unarchive workflow cannot be established through that list, so this tool does not promise undo. Removing exclusions can broaden matching. Batch responses retain successfully returned IDs even when other items fail; never replay an uncertain creation or archive.

`pinterest_keyword_metrics` reads country-wide native search-frequency ranges for `CA`, `GB`, `US`, `IE`, `AU` and `NZ`. Live verification found that the endpoint rejects other markets, including `DE`; the tool rejects unsupported countries without substituting a different market. Values such as `5M+` stay strings and missing entries remain unavailable; these are not account-performance counts or observed campaign results.

## Audiences and customer sources

`pinterest_audiences` explicitly chooses `OWNED` or `RECEIVED` sources and labels ownership. `pinterest_get_audience` requires native advertiser ownership and returns current configuration, processing state, a snapshot and an inline copy-edit form. `pinterest_update_audience` changes only supplied name/description; `null` clears the description, while omitted copy, rules and source type are preserved. Processing size/status changes do not invalidate a copy snapshot. A snapshot compares current content; it is not a monotonic provider version or atomic conditional-write token.

`pinterest_create_audience` supports four typed definitions: `CUSTOMER_LIST`, `VISITOR`, `ENGAGEMENT` and `ACTALIKE`. Customer-list and seed-audience definitions bind a current source hash. Visitor definitions verify owned conversion tags and require an explicit historical `prefill` choice. Engagement definitions check campaigns, ads and Pins for ownership and domains against the advertiser owner's native website inventory. `pinterest_audience_sources` reads that credential-global website inventory only when the token user matches the advertiser owner; it never claims or verifies a website. A listed domain is not proof of native engagement-audience eligibility. All four workflows leave audiences unattached to ads and do not install tracking or send events; native eligibility and processing checks remain authoritative.

`pinterest_audience_usage` reads all visible ad-group statuses, owned derived audiences, and both advertiser/business sharing edges. Targeting roles and serving statuses are included in its context hash. Inventory is bounded to5,000 items per collection; missing targeting configuration, unknown derived-source formats, incomplete pages or denied sharing reads cannot establish an unused audience. `pinterest_replace_audience_rule` requires matching configuration and complete usage context, preserves the audience type, rejects shared-rule edits and rechecks every source. This replaces the complete rule and can affect linked ad groups. `pinterest_remove_audience` requires an explicit permanent-removal confirmation plus complete, current, empty usage/sharing checks and uses native PATCH `operation_type: REMOVE`. Pinterest provides no atomic usage freeze; concurrent native changes remain possible.

Customer-list metadata and matching readiness are available through `pinterest_customer_lists` and `pinterest_get_customer_list`. `pinterest_create_customer_list` and `pinterest_update_customer_list_records` accept up to10,000 unique, correctly normalized SHA-256 EMAIL/IDFA/MAID records per call and require confirmation of data rights. Creation sends explicit `is_nca: false` by default; that immutable matching choice cannot be edited through membership updates. Native membership writes use `ADD`/`REMOVE`; previews show only batch count and digest, and native errors/metadata never return identifiers or exception contents. Existing batch counters and metadata are snapshot-bound. Processing and matching are asynchronous, and acceptance does not prove matched members or eligibility. Pinterest requires at least100 matched accounts for serving and exposes no customer-list container delete endpoint in this contract. Removing an audience does not delete its customer-list container.

## Verification

Live verification covered configuration/discovery/estimate reads, paused CBO campaign and ad-group creation, name/locale/bid/budget changes, rejection of a child budget under CBO, and archive cleanup. Direct resource reads and corrected CSV-filtered lists confirmed the QA resources archived. Real Pin-backed ad creation and Pin media reads require eligible existing Pins and their provider permissions; contract tests do not establish those grants. Original Pin/board/video operations have native-wire and policy tests; existing-connection live results are recorded separately from local verification.
