# Google conversion management

These named tools use the shared CLI/MCP registry and policy engine. Every mutation first sends a native `validateOnly: true` request and returns an approval token. An identical apply call re-reads native configuration, verifies the snapshot and policy, validates again, and then executes. Conversion values are whole currency units, independent of advertising budget caps in micros.

## Tracking ownership and configuration

`google_conversion_tracking_context` returns the selected customer's currency, native tracking configuration, conversion owner and `snapshot_hash`. It does not enable tracking, accept customer-data terms or redirect a write to a manager account. Use its hash as `expected_context_hash` for `google_create_conversion_action`.

`google_conversion_actions` lists available configurations and tag snippets. It orders native decimal IDs without number conversion. Continue `next_cursor` as `after_action_id`, preserving account, filters and limit. Removed actions are excluded unless `include_removed` is true. `google_get_conversion_action` returns an action, its tracking context, an ownership-based `editable` flag and `snapshot_hash`. Native type/field restrictions still apply. Shared or system-owned configurations remain read-only; selecting a manager requires that manager's explicit project authorization.

`google_create_conversion_action` supports `UPLOAD_CLICKS`, `UPLOAD_CALLS` and `WEBPAGE`, with explicit category and counting mode. `primary_for_goal` defaults to false. Creation installs no tags, creates no campaign goal association and submits no events. A secondary action can still be biddable when used in a custom conversion goal; the flag does not override custom goals.

`google_update_conversion_action` requires `expected_action_hash` and preserves omitted fields through exact masks, including omitted nested value settings. It supports name, category, counting, primary-goal classification, windows, phone-call duration, default value/currency and attribution. Type and ownership remain immutable. `google_set_conversion_action_status` requests `ENABLED` through a status update or `REMOVED` through the native remove operation. The live API rejected writing `REMOVED` directly to the status field. Enabling a removed action is subject to native type restrictions. `HIDDEN` is readable but excluded from the write schema after a live native `BLOCKED_VALUE` denial. Legacy `IMPORTED_LEAD` is also excluded after a live creation denial; native type/category restrictions remain authoritative. `google_remove_conversion_action` uses the same native remove operation. Configuration, status and removal can affect reporting and bidding goals that use an action.

## Legacy Google Ads imports

`google_upload_click_conversions`, `google_upload_call_conversions` and `google_upload_conversion_adjustments` accept 1–2,000 records for one action, with `expected_action_hash`. The action must be enabled and owned by the selected customer's verified conversion-tracking owner. Google identifies conversion actions by ID during uploads and can ignore the resource-name customer prefix; Adport therefore verifies native ownership and tracking context rather than relying on that prefix.

Google restricts legacy click uploads for new adopters. **New click-import integrations require the Data Manager API**, its API enablement and `datamanager` OAuth scope. The named click uploader here is the legacy Google Ads service for eligible existing integrations. Data Manager ingestion remains a separate implementation gap; Adport does not silently switch APIs, enable it or expand OAuth grants. See Google's [current conversion upload access rules](https://developers.google.com/google-ads/api/docs/best-practices/quotas#conversion_upload_service) and [Data Manager setup](https://developers.google.com/data-manager/api/devguides/quickstart/set-up-access).

Click imports preserve every captured GCLID/GBRAID/WBRAID and optionally accept order IDs, cart data, external attribution, environment, customer type and enhanced lead identifiers. Only separately supplied normalized SHA-256 email/phone identifiers are accepted. Their consent must explicitly grant `ad_user_data`, and native customer-data terms must already be accepted. Consent is never invented. Braid-only combinations that would silently discard supplied user/cart data are rejected. External attribution must match the action's model. Custom conversion variables and Data Manager-only session/IP fields are outside these typed upload tools.

Call imports require the actual E.164 caller ID, call start, later conversion time, value and currency. Adjustment imports support `RETRACTION`, `RESTATEMENT` and `ENHANCEMENT`. Use the original order ID, or a supported original GCLID/date-time pair. Restatements specify the final adjusted total, rather than a delta; later restatements need a later adjustment time. Enhancements require an order ID and up to five separate hashed identifier objects, including supported address information. No conversion tool normalizes or hashes raw personal data automatically.

All legacy uploads set `partialFailure: true`. Errors embedded in a successful HTTP response are inspected; a validation error does not produce a pending approval. After apply, `result.details` gives a batch hash, native job/request IDs when present, and indexed `CONFIRMED`, `FAILED` or `UNKNOWN` outcomes. Confirmed means the native response processed that row, not that attribution or reporting has completed. Mixed outcomes return warnings through the CLI/MCP response and widget; wholly failed or unconfirmed batches return an error. Neither path retries records automatically. Inspect native diagnostics and outcomes before another upload, especially for records without an order ID.

Previews, Adport audit summaries and returned outcome metadata omit event identifiers and native echoes. Full inputs are stored in the normal access-controlled pending operation so the identical-arguments gate can verify them. Approval expires at the configured TTL; the pending store's cleanup removes expired entries. Native upload errors are reduced to row indexes, field paths, enum codes and request IDs. The versioned review widget displays warnings and passes them to host context without a reusable approval token.

The contracts are pinned to Google's [v25 conversion upload service](https://github.com/googleapis/googleapis/blob/492a18f4cccdac9f4fd7d5f5e5bea3db8b64aec0/google/ads/googleads/v25/services/conversion_upload_service.proto), [adjustment service](https://github.com/googleapis/googleapis/blob/492a18f4cccdac9f4fd7d5f5e5bea3db8b64aec0/google/ads/googleads/v25/services/conversion_adjustment_upload_service.proto) and [conversion action resource](https://github.com/googleapis/googleapis/blob/492a18f4cccdac9f4fd7d5f5e5bea3db8b64aec0/google/ads/googleads/v25/resources/conversion_action.proto). The live field catalog was also checked because GAQL selects tracking/value settings through their individual fields.
