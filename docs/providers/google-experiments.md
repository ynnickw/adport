# Google experiments

The named experiment tools share the same registry and preview/apply policy in MCP, the hosted tool API and the CLI. They use Google Ads v25 native experiment/arm services. Read tools use the existing Google Ads OAuth permission; no broader grant is requested.

`google_experiments` lists configuration, lifecycle state and the latest native operation, with ID continuation. `google_experiment_context` returns the selected customer's currency/timezone, experiment/arms and their base, draft and materialized treatment campaigns with daily budgets and bidding configuration. Before creation, pass `base_campaign_id` and retain `base_snapshot_hash`. Before editing, pass `experiment_id` and retain `experiment_snapshot_hash`. Graduation also needs `campaign_budget_id` and `budget_snapshot_hash`.

Every mutation needs the applicable current hash as `expected_base_hash`, `expected_experiment_hash` or `expected_budget_hash`. The hash is checked at preview and apply. It covers the returned configuration, including associated campaigns/budgets; it does not freeze every underlying ad, keyword or target. Google has no atomic compare-and-set, so concurrent changes remain possible after a read.

## Draft setup and editing

`google_create_experiment` creates one SETUP experiment and its control/treatment arms in one atomic native request. It supports the system-managed types `SEARCH_CUSTOM`, `DISPLAY_CUSTOM`, `HOTEL_CUSTOM`, `YOUTUBE_CUSTOM` and `PMAX_REPLACEMENT_SHOPPING`. The base must be a matching native BASE campaign with an available non-shared daily budget. Traffic must total 100% and arm names must be unique. Native type, campaign eligibility, date and arm-count restrictions still apply. Video requires its explicit subtype; optional Performance Max replacement settings preserve integer micros and compatible bid targets.

Google generates in-design treatment campaigns from the control. Adport keeps SETUP unscheduled, confirms all created identities, validates/applies required PAUSED coercions only to the new owned drafts, then reads back their statuses and individual approved budget bounds. It does not pause the base. A preview cannot validate the pause of a draft that has no assigned ID yet; with paused creation enabled, `serverValidated: false` explicitly reports this deferred follow-up even when native atomic creation validation succeeds. Partial follow-up failure returns acknowledged resource IDs and never schedules or automatically retries creation.

`google_update_experiment` changes only supplied metadata, dates and goals through exact native masks. `google_add_experiment_arms` creates new treatments and rebalances supplied existing arms atomically; new drafts get the same ownership, pause and budget checks. `google_update_experiment_arms` edits names/traffic; `google_remove_experiment_arms` removes owned arms and rebalances the remainder. Arm setup changes require SETUP and a final set with one control and 100% traffic, or removal of the whole set. `google_remove_experiment` removes the verified experiment. Google may also remove associated draft/treatment copies; the base campaigns are retained.

Use `include_drafts: true` with `google_gaql` or `google_ads` to inspect draft entities and actual RSA copy. Default reads exclude native drafts. Named campaign/ad mutation preflights and scoped asset associations explicitly include drafts, allowing existing ad-group, keyword, RSA, bidding, budget and association tools to operate on native draft IDs through their normal policy gate. This does not provide complete campaign-type-specific editing for every experiment variant.

## Lifecycle and completion

`google_schedule_experiment` materializes and schedules a SETUP experiment. Google's action exposes no paused-creation flag and can start serving, so Adport blocks scheduling while `paused_creation` is enabled. Policies that allow serving still require `confirm_serving_changes: true`, the current snapshot, a native `validateOnly` preview and the identical-arguments apply token. This flag does not override a policy block.

`google_end_experiment` ends experiment serving immediately; treatment campaigns remain. `google_promote_experiment` applies native treatment configuration to the base. `google_graduate_experiment` graduates one verified materialized treatment to an independent campaign using a current, owned, non-shared daily budget unused by other campaigns. Promotion and graduation require explicit serving confirmation. Previews report budget deltas in micros, with conservative configured ceilings for scheduling/promotion. Native traffic splitting is not a guarantee of additional independent spend.

Scheduling and promotion return an asynchronous operation. An apply acknowledgement returns `ACCEPTED_FOR_PROCESSING` and `processed: false`; the widget displays **Processing pending**. Use `google_experiment_operation` to poll only the current account-scoped operation reported by the verified experiment, then inspect `google_experiment_async_errors`. States distinguish processing, native operation success, failure and unknown completion evidence. A completed operation alone does not prove serving or performance. Async errors support native pagination and return enum codes/field paths without sensitive value echoes. No operation is automatically retried, canceled or resubmitted.

These tools implement the [system-managed workflow](https://developers.google.com/google-ads/api/docs/experiments/system-managed) and [asynchronous error contract](https://developers.google.com/google-ads/api/docs/experiments/async-errors), pinned to the official [v25 experiment service](https://github.com/googleapis/googleapis/blob/492a18f4cccdac9f4fd7d5f5e5bea3db8b64aec0/google/ads/googleads/v25/services/experiment_service.proto) and [arm resource](https://github.com/googleapis/googleapis/blob/492a18f4cccdac9f4fd7d5f5e5bea3db8b64aec0/google/ads/googleads/v25/resources/experiment_arm.proto). Intra-campaign, asset-optimization and campaign-mix creation need separate native workflows and remain outside these setup tools.
